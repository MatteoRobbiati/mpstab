Engines¶

Engines are the computational backends that perform low-level state operations. Each kind has an abstract interface, so a custom engine can be swapped in.

Two Engine Types:

  1. Stabilizer Engines: Handle Clifford gates efficiently

  2. Tensor Network Engines: Manage non-Clifford effects via MPO

Stabilizers engine backed by stim.

backpropagate_at(observables: Sequence[str], breakpoints: Sequence[int], clifford_circuit: Circuit) → list[source]¶

Backpropagate each observable through its own prefix of clifford_circuit with one stim tableau pass.

The circuit is simulated once, a segment at a time in breakpoint order, and each observable is conjugated by the inverse tableau of its prefix, so the cost is one pass over the circuit plus one conjugation per observable.

Raises:

ValueError – on a breakpoint outside [0, len(clifford_circuit.queue)].

backpropagate_many(observables, clifford_circuit: Circuit) → list[source]¶

backpropagate() every observable through the same circuit.

The circuit’s U^dag tableau is built once and cached, so a whole Hamiltonian costs one stim simulation plus one tableau lookup per term, and repeated calls on an unchanged circuit skip the simulation too.

instructions(circuit: Circuit) → list[source]¶

One stim instruction line per gate of circuit, None for gates that leave the Pauli frame untouched.

stim parses a whole program from text far faster than it appends instructions one call at a time, so circuits are assembled as text.

Raises:

ValueError – on a non-Clifford rotation angle, or a gate with no stim equivalent. Unsupported gates fail loudly rather than being dropped, which would silently give a wrong Pauli frame.

class mpstab.engines.tensor_networks.quimb.QuimbEngine(backend: str = 'numpy', svd_cutoff: float | None = None)[source]¶

Bases: TensorNetworkEngine

MPS evolution and MPO expectation values via quimb.

States are quimb MatrixProductState objects and operators quimb MatrixProductOperator objects, so the MPS also feeds quimb’s DMRG.

On the numpy backend the engine only supplies the representation hooks (state_sites(), operator_sites(), operator_from_sites()) and every algorithm is the shared one of TensorNetworkEngine. The jax and torch backends, which may need to differentiate through the state, run quimb’s own contractions and compressions instead.

apply_pauli_sum(state_circuit: MatrixProductState, paulis, coefficients, max_bond_dimension: int | None) → MatrixProductState[source]¶

A new state sum_t c_t P_t |state>.

The terms are stacked into block-diagonal MPOs of _PAULI_SUM_CHUNK terms each, compressed exactly and summed (a sum of local strings keeps a small bond), and the result is applied to the state and compressed to max_bond_dimension.

copy_state(state_circuit: MatrixProductState)[source]¶

An independent copy of the state.

On the numpy backend the copy has its own tensors but shares their arrays: the shared kernels, like quimb’s own operations, replace a tensor’s array rather than write into it, so neither state can change the other. The cached canonical form is carried over, so the copy needs no re-canonicalization. Other backends get a deep copy.

expval(state_circuit: MatrixProductState, operator: MatrixProductOperator)[source]¶

Expectation value of operator on state_circuit, normalised.

On the numpy backend this is the shared algorithm. Otherwise the whole <psi|O|psi> network is contracted by quimb: the operator MPO has upper (output) index k{i} and lower (input) index b{i}, so the ket is reindexed k -> b while the conjugated bra keeps k{i} to meet the output. Reindexing the bra instead would evaluate <psi|O^T|psi>, which differs for any operator with an odd number of Y’s.

Building blocks for a new engine: the array backend the shared kernels run on, and a ready-made site-array state and operator.

Tensor-network engine on NVIDIA GPUs, backed by cuTensorNet.

States and operators live on the GPU as CuPy site arrays (SiteMPS, SiteMPO). The engine supplies only the representation hooks of TensorNetworkEngine; every algorithm (windowed Pauli rotations, expectation values, operator conjugation, transition amplitudes) is the shared one, run on the GPU through a Linalg whose QR and SVD are cuTensorNet’s tensor decompositions (cuquantum.tensornet.tensor.decompose). Expectation values of general operators are contracted as one network by cuTensorNet’s contract, with its path optimizer.

Truncation uses the same "rsum2" rule as QuimbEngine (the singular values of each split are read back to the host to pick the kept rank), so both engines produce the same states up to floating-point roundoff.

Needs cupy and cuquantum, both imported when the engine is first built: pip install "mpstab[cutensornet]" (CUDA 12 wheels). The engine runs on CuPy’s current device; select another GPU with cupy.cuda.Device(i).use().

Native Engines¶

Pure-Python implementations of the two interfaces, kept as readable examples of what an engine does rather than for performance. They give the same expectation values as stim and quimb, but are slower and cover less: the native tensor-network engine has no operator-side conjugation (so no head/tail split in HQSMPO) and no DMRG.

Pure-Python stabilizers engine.

Selecting Engines¶

Engines are automatically selected based on your circuit type and parameters:

from qibo import Circuit, gates
from mpstab import HSMPO
from mpstab.models.ansatze import HardwareEfficient

clifford_circuit = Circuit(nqubits=10)
# Add only Clifford gates
for q in range(10):
     clifford_circuit.add(gates.H(q))
     clifford_circuit.add(gates.CNOT(q0=q%10, q1=(q+1)%10))

# Clifford circuit - uses stabilizer engine only
simulator = HSMPO(ansatz=clifford_circuit)

# Constructing a circuit with also magic gates
mixed_circuit = HardwareEfficient(
     nqubits=10,
     nlayers=3,
)

# Mixed circuit with bond limit - uses both engines
simulator = HSMPO(
    ansatz=mixed_circuit,
    max_bond_dimension=32  # Enables tensor network engine
)

For detailed guidance, see Working with Engines

Engine Interface¶

All engines implement standardized interfaces for compatibility.

Base Engine Classes:

from mpstab.engines import StabilizersEngine, TensorNetworkEngine

The evolutors never look inside an engine’s states or operators: everything they need goes through these methods. tests/test_engine_agnostic.py enforces this with an engine whose states and operators expose nothing.

A tensor-network engine splits into a representation, which is engine-specific, and the algorithms, which are implemented once in TensorNetworkEngine as concrete methods. The algorithms (windowed Pauli rotations, expectation values, operator conjugation, transition amplitudes) are the kernels of mpstab.engines.tensor_networks._mps_kernels. They run on the site arrays the representation exposes, with the array module and factorizations of the engine’s linalg: NumPy and LAPACK for quimb, CuPy and cuTensorNet for the GPU engine. Every engine therefore truncates with the same "rsum2" rule (svd_cutoff).

TensorNetworkEngine methods

Role

build_circuit_mps, pauli_mpo

Abstract: build a state and a Pauli-string operator.

state_sites, state_from_sites

Representation: the state as (left, phys, right) arrays in mixed canonical form, which every state-side algorithm runs on, and back from such arrays.

operator_sites, operator_from_sites, operator_site_arrays, pauli_string_of

Representation: operators as (left, 4, right) arrays and back, and out of the engine as numpy (left, right, out, in) arrays (the head/tail split of HQSMPO and its measurement routes).

linalg, copy_state, bond_dimension

Representation, with defaults: NumPy arrays, a deep copy, no bond report.

svd_cutoff, truncation_cutoff

The "rsum2" cutoff every shared algorithm truncates with (None keeps quimb’s default, 1e-10).

process_start_method, worker_context

How the processes of noisy_expectation and gradient start: "spawn" for an engine holding a GPU context.

has_site_view, has_operator_sites, has_pauli_sum

Whether the shared algorithms apply; by default, whether the hooks above are implemented. An engine without them keeps its own expval and conjugate_operator. With a site view and Pauli sums, the adjoint gradient runs fused on the shared kernels.

expval, pauli_expvals, pauli_rot, squared_norm, pauli_transitions, rotation_operator, apply_rotation, conjugate_operator, conjugate_operator_many, site_arrays

Concrete, shared: implemented on the site view. An engine may still override them, as QuimbEngine does on jax and torch to stay differentiable, and the native engine does to run its own Vidal-form algorithms.

apply_pauli_sum

Optional: the adjoint gradient (HSMPO.gradient(method="adjoint")); method="flips" does without it. QuimbEngine only.

pauli_sum_mpo, minimize_energy

Optional: DMRG (HSMPO.minimize_expectation). QuimbEngine only.

circuit_truncation_fidelity

Optional: HSMPO.truncation_fidelity_pure_tn. QuimbEngine only.

An optional method an engine does not implement raises NotImplementedError only when the feature that needs it is used.

A stabilizers engine is where every Clifford circuit is simulated: the Clifford part of the circuit, and the residual a head resynthesis leaves behind. The evolutors, the noise compiler and the measurement routes only ask it for backpropagated Pauli strings, so stim is imported by StimEngine alone. Clifford circuits travel as qibo circuits (e.g. residual_circuit), and signed Pauli products are plain Pauli algebra (mpstab.pauli.pauli_product()).

StabilizersEngine methods

Needed for

backpropagate

Required: dressing observables with the Clifford circuit.

backpropagate_many

Optional, with a generic default an engine may override to share work across observables.

backpropagate_at

Dressing each magic gate and noise event with the Clifford gates before it. The default replays each prefix through backpropagate; StimEngine overrides it with a single tableau pass.

clifford_images, is_identity

Concrete, built on backpropagate_many: comparing Clifford circuits, e.g. checking whether the resynthesis residual of HQSMPO is trivial.
